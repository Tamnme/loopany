One thing worth naming: you solved the *same* problem two different ways.

```rust
fn fill_vec(vec: Vec<i32>) -> Vec<i32> { let mut vec = vec; /* … */ }  // move_semantics1
fn fill_vec(mut vec: Vec<i32>) -> Vec<i32> { /* … */ }                 // move_semantics3
```

Both correct, and they mean the same thing — `mut` on a parameter *is* that rebind, written
once. In `move_semantics2` you reached for `.clone()`, also the intended answer there, but it
copies the whole buffer. Today's concept is the cheap way to say "let me use it without
taking it".

### Concept

A move isn't the only option. You can hand out a **reference** — borrow the value, use it,
give it back:

```rust
let v = vec![1, 2, 3];
let r = &v;            // borrow; v still owns the buffer
println!("{}", r.len());
println!("{v:?}");     // fine — v was never moved
```

`&v` is a **shared** borrow: read-only, and you may have as many at once as you like.
`&mut v` is an **exclusive** borrow: you can mutate through it, and while it is alive nothing
else may touch `v` — no second `&mut`, no `&`, not even `v` by name.

That is the whole borrow checker in one line: *many readers, or one writer, never both*. It
is also why data races can't compile in safe Rust.

### Concept

Same idea as yesterday, shorter. A **binary search tree** is nodes with a `left` and a
`right` child, obeying exactly one rule:

> everything in the left subtree < the node < everything in the right subtree

Here is one, already built:

```
        50
       /  \
     30    70
    /  \   / \
  20   40 60  80
```

To find a value, start at the root and compare. Smaller → go left. Bigger → go right. Equal →
found. Each comparison throws away an entire branch, so the cost is the tree's **height**, not
its size: a balanced million-node tree is about twenty comparisons.

The catch is that the shape depends on **insertion order**. Insert `10, 20, 30, 40` in that
order and every value goes right, forever — a straight line, height 4, search `O(n)`. Same
rule, obeyed perfectly; nothing in it mentions balance.

| op | balanced | worst case |
|---|---|---|
| search / insert | `O(log n)` | `O(n)` |

<details>
<summary>Worked answer — open only after you've written yours</summary>

**Q1 — compare `50`, `70`, `60`: three comparisons.** 60 > 50 → right to 70; 60 < 70 → left
to 60; found.

`35`: 35 < 50 → left to 30. 35 > 30 → right to 40. 35 < 40 → left, and that slot is empty.
So **`35` becomes 40's left child.** Note you always end at an empty slot hanging off an
existing node — insertion never restructures anything above it.

**Q2 — `60` breaks it.** Each pair checks out on its own: 30 < 50 ✓, 60 > 30 ✓. But `60`
lives in **50's left subtree**, and 60 > 50. Comparing only against the parent is not enough,
which is why a real validity check carries a `(min, max)` window down the recursion: on
entering 30's subtree the window becomes "must be < 50", and 60 fails it.

Read it out loud instead: an in-order walk (left, node, right) of a valid BST prints sorted
values. This one prints `30, 60, 50`. Out of order — same bug, different angle.

</details>
