## Track A · Rust

### Concept

A function is `fn name(params) -> ReturnType { body }`. Two rules trip everyone up
coming from Python or JS:

**Parameter types are mandatory.** Rust never infers them — the signature is a
contract the compiler checks at every call site.

```rust
fn greet(name: &str, times: u8) { … }   // both types required
```

**The last expression is the return value — if it has no semicolon.**

```rust
fn square(x: i32) -> i32 {
    x * x        // no semicolon → this is the return value
}

fn broken(x: i32) -> i32 {
    x * x;       // semicolon → statement, returns () → type error
}
```

A semicolon turns an expression into a statement and throws its value away. That one
character is the difference between compiling and `expected i32, found ()`.

### Concept

Yesterday's dynamic array bought `O(1)` indexing with one contiguous block. A **linked
list** gives that block up entirely. Each element is a **node** holding a value plus a
pointer to the next node, and the nodes can sit anywhere in memory:

```
head → [ 3 | •-]→ [ 7 | •-]→ [ 1 | •-]→ [ 9 | / ]
```

The `/` is the null/`None` at the end — that is how you know you've run out.

Because there is no `start + i × size` arithmetic to do, **there is no random access**.
To reach index `i` you start at `head` and follow `i` pointers. Reading the middle of a
million-node list means 500,000 hops: `O(n)`.

What you get in exchange: **no shifting**. Inserting at the front of an array means
moving every existing element up one slot — `O(n)`. Inserting at the front of a linked
list is three assignments regardless of length:

```
new.next = head          head → [ 5 | •-]→ [ 3 | •-]→ [ 7 | ... ]
head     = new                   ^ new node, nothing else moved
```

That's `O(1)`, always. Same for deleting the front. And *if you are already standing at
a node*, splicing a new node in after it is `O(1)` too — you only rewrite two pointers,
you never touch the rest of the list.

The trade in one table:

| | dynamic array | singly linked list |
|---|---|---|
| `list[i]` | `O(1)` | `O(n)` |
| push/pop **back** | amortized `O(1)` | `O(n)`¹ |
| insert/delete **front** | `O(n)` | `O(1)` |
| memory per element | the value | the value **+ one pointer** |

¹ unless you also keep a `tail` pointer.

Neither wins. Arrays win when you index; linked lists win when you insert and delete at
ends you're already holding. That's why the next two structures Track B implements —
`Stack` and `Queue` — can be built on *either*, and why the choice matters.

<details>
<summary>Worked answer — open only after you've written yours</summary>

**Q1 — 699 hops (700 if you count arriving at `head`), `O(n)`.** There is no address
arithmetic available, so the only way to node `i` is to walk `i` pointers from the head.
Double the list and you double the walk — linear. Note this makes a "binary search on a
linked list" pointless: the algorithm needs `O(1)` access to the midpoint, and here
finding the midpoint already costs `O(n)`.

**Q2 — array `O(n)`, linked list `O(1)`.** The array must shift all `n` existing
elements up one slot to free index 0. The linked list moves nothing: point the new
node's `next` at the old head, then point `head` at the new node. Two writes, whatever
the length.

**Q3 — you need the *previous* node, and finding it costs `O(n)`.** Deleting node `X`
means making `X`'s predecessor point at `X.next`. A singly linked node only knows what
comes *after* it, so the only way to find the predecessor is to walk from `head` again —
which is why "delete this node" is `O(n)` in a singly linked list even when you already
have the node. Two standard fixes: a **doubly linked list** (each node also stores
`prev`, making it `O(1)` at the cost of another pointer per node), or the copy trick —
copy the *next* node's value into `X` and delete the next node instead, which works for
every node except the last.

**Q4 — about 8 KB versus about 16 KB.** The array stores 1,000 × 8 bytes of values in
one block. Each linked-list node stores the 8-byte value *plus* an 8-byte pointer, so
~16 bytes a node, ~16 KB total — double, before you count allocator overhead per node
and the cache misses from the nodes being scattered instead of contiguous. Pointer
overhead is the linked list's hidden third cost, alongside `O(n)` access.
</details>
