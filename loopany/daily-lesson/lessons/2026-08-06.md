single most common Rust slicing mistake.

One improvement, and it closes a loop from yesterday's own concept — the lesson said
"`get()` exists when you'd rather have an `Option` than a crash", and this is the shape:

```rust
let nice_slice = a.get(1..4).expect("range in bounds");
assert_eq!([2, 3, 4], nice_slice);
```

`&a[1..4]` **panics** if the range runs off the end; `a.get(1..4)` returns
`Option<&[i32]>` — `Some` if the range fits, `None` if it doesn't. Here the array is a
literal five elements long so it can never fail and the indexing form is the right call.
But the moment the range comes from a variable or user input, `get()` is what stops a
panic from being your error handling. Ranges work in `get()` exactly like they do in `[]`.

The official solution differs in one real way — it shows the **inclusive** range:

```rust
let nice_slice = &a[1..=3];   // same three elements as 1..4
```

`..=` includes the end index. `1..4` and `1..=3` are the same slice, and which one reads
better depends on how you think about the boundary: "up to but not including 4", or
"elements 1 through 3". Use whichever matches the sentence in your head.

### Concept

Yesterday ended on a cliff: an array's length is part of its type, so it cannot grow.
**`Vec<T>` is the thing that lifts that constraint**, and it is also — not by coincidence —
the first structure you will implement in Track B's stage B2. So read this as a spec.

A `Vec<T>` is exactly **three machine words**:

```
     ptr ──────────────► [ 10 | 20 | 30 | _ | _ | _ ]   ← the heap
     len = 3                                             capacity = 6
     capacity = 6
```

`len` is how many elements you have. `capacity` is how many you could hold before it must
reallocate. That gap between them is the amortized doubling you costed out in lesson 3 —
`Vec` is that analysis made concrete.

```rust
let mut v = Vec::new();       // empty, no heap allocation yet
v.push(10);                   // now it allocates
v.push(20);
println!("{} of {}", v.len(), v.capacity());   // 2 of 4

let w = vec![10, 20, 30];     // the macro, when you know the elements up front
```

`push` needs `mut` — growing is mutation. And `Vec::new()` on its own can't know its type;
the first `push` tells the compiler it's a `Vec<i32>`.

**The payoff for yesterday: a `Vec<T>` *is* a slice, whenever you want it to be.**

```rust
let v = vec![1, 2, 3, 4, 5];
let middle = &v[1..4];        // &[i32] — same slice syntax as the array
println!("{}", v.len());      // len() is a slice method, not a Vec method
```

Every method you learned on `&[T]` works on a `Vec<T>` for free, because `Vec` derefs to a
slice. That is the whole reason yesterday came first: slices are the shared vocabulary, and
`Vec` just adds ownership and growth on top.

Iterating borrows rather than consumes:

```rust
for x in &v { println!("{x}"); }              // v still usable after
let doubled: Vec<i32> = v.iter().map(|x| x * 2).collect();
```

`.iter()` hands out references, `.map()` transforms each, `.collect()` builds the new
`Vec`. That last line is the idiom you'll reach for constantly — and it's `vecs2`.

### Concept

An array gives you `O(1)` access **by index**. That's cheap because an index is just
arithmetic: `address = start + i × size`. But almost nothing you actually want to look up
is numbered `0, 1, 2` — you want to look up a *username*, a *word*, a *phone number*.

A **hash table** buys `O(1)` access **by key** by building a bridge to that index:

```
key "grape"  ──h()──►  1049237  ──% 8──►  bucket 3  ──►  array slot 3
              hash      a number         fold into range
```

The **hash function** turns a key of any shape into a number. Then you fold it into the
table's range with `bucket = h(key) % capacity`. Three requirements, and they're all
non-negotiable:

1. **Deterministic** — the same key must always give the same number, or you'd never find
   what you stored.
2. **Fast** — it runs on every insert *and* every lookup, so it's in the hot path.
3. **Uniform** — it must scatter keys evenly across buckets. A hash that sends everything
   to bucket 0 is *correct* and *useless*: you'd have a linked list with extra steps.

**Collisions are not a bug you can engineer away.** There are infinitely many possible
keys and finitely many buckets, so two keys *must* eventually land in the same one — the
pigeonhole principle. A hash table isn't a design that avoids collisions, it's a design
that **handles them cheaply**. Two ways:

**Separate chaining.** Each bucket holds a small list. Colliding entries join the list at
that bucket; lookup hashes to the bucket, then walks the list comparing keys.

```
bucket 0: →
bucket 1: → ("cat", 9)
bucket 2: →
bucket 3: → ("grape", 4) → ("melon", 7)     ← both hashed to 3
```

**Open addressing (linear probing).** No lists — everything lives in the array itself. If
slot 3 is taken, try 4, then 5, until you find a free one. Lookup does the same walk. One
contiguous array, cache-friendly, but deletion gets fiddly (removing an entry can break
the probe chain that ran through it).

**The load factor is what keeps it `O(1)`.** α = `len / capacity`. As α climbs, chains
lengthen and probes run longer, so real implementations **resize** — allocate a bigger
array (usually double) once α passes ~0.75, and **rehash every existing entry into it**.
Not copy: rehash. `bucket = h(key) % capacity`, and `capacity` just changed, so every old
bucket number is now wrong.

So the honest cost table:

| op | average | worst case |
|---|---|---|
| insert | `O(1)` amortized | `O(n)` |
| lookup | `O(1)` | `O(n)` |
| delete | `O(1)` | `O(n)` |

The worst case is every key colliding into one bucket — then you're linearly scanning a
list of `n`, and the hash bought you nothing. That's why "uniform" was requirement 3.

<summary>Worked answer — open only after you've written yours</summary>

**Q1 — slots 0, 1, 2 hold `3, 4, 5`; `head = 0`, `tail = 3`.** Step by step, with `tail`
being where the *next* write goes:

```
start                 head=3 tail=3 len=0   [ _ | _ | _ | _ | _ ]
enqueue 1 → slot 3    head=3 tail=4 len=1   [ _ | _ | _ | 1 | _ ]
enqueue 2 → slot 4    head=3 tail=0 len=2   [ _ | _ | _ | 1 | 2 ]   ← tail wrapped
enqueue 3 → slot 0    head=3 tail=1 len=3   [ 3 | _ | _ | 1 | 2 ]
dequeue   → 1         head=4 tail=1 len=2   [ 3 | _ | _ | _ | 2 ]
dequeue   → 2         head=0 tail=1 len=1   [ 3 | _ | _ | _ | _ ]   ← head wrapped
enqueue 4 → slot 1    head=0 tail=2 len=2   [ 3 | 4 | _ | _ | _ ]
enqueue 5 → slot 2    head=0 tail=3 len=3   [ 3 | 4 | 5 | _ | _ ]
```

Front to back that's `3, 4, 5` — the right FIFO answer. Two things to take from the trace.
**`3` was written to slot 0 while the queue's front was still at slot 3** — the queue was
physically wrapped around the end of the array and nothing was wrong with that. And notice
`head == tail == 3` at the start (empty) and `head = 0, tail = 3` at the end holding three
elements — if you'd filled all five, you'd get `head == tail` again. That's the ambiguity
lesson 6 warned about: `head == tail` alone can't tell empty from full, which is why the
`len` column is in the trace and will be a field in your `Queue` struct.

**Q2 — both land in bucket 3, and it fails *uniformity*.** `"ab"` = 1 + 2 = 3, `3 % 8 = 3`.
`"ba"` = 2 + 1 = 3, `3 % 8 = 3`. It's deterministic (same word, same answer, always) and
it's fast (one pass, a few additions), so requirements 1 and 2 hold — it's requirement 3
that breaks. Because addition is commutative, **every anagram collides**: `"listen"`,
`"silent"` and `"enlist"` are all one bucket. Worse, short English words cluster in a
narrow range of sums, so buckets in the middle get hammered while the ends stay empty. Real
hash functions defeat this by making **position** matter — the classic shape is
`h = h * 31 + c` per character, so moving a letter changes the result completely.

**Q3 — separate chaining: into a list hanging off that bucket. Open addressing: into a
different slot of the same array.** Chaining accepts the collision — bucket 3 becomes a
list, the new entry joins it, and lookup hashes once then walks that short list. Open
addressing refuses to allocate anything extra — the entry goes to the next free slot
(`probe 4, 5, 6…`), so a collision *displaces* the entry rather than nesting it. The
trade: chaining degrades gracefully and deletes cleanly but pays a pointer and an
allocation per entry; probing is one flat cache-friendly array but needs a tombstone
marker on delete, because a plain empty slot would cut short a probe chain that ran
through it and hide entries beyond.

**Q4 — because the bucket number is computed *from* the capacity, and the capacity
changed.** `bucket = h(key) % capacity`. A key whose hash is 19 was in bucket `19 % 8 = 3`;
in the new table it belongs in `19 % 16 = 3` — that one happens to match. But a key hashing
to 11 was in `11 % 8 = 3` and now belongs in `11 % 16 = 11`. Copy it to slot 3 and *no
future lookup will ever find it*, because lookup will compute 11 and look in 11. So resize
means walking every existing entry, recomputing `h(key) % new_capacity`, and reinserting —
an `O(n)` operation. That's the same amortization argument as `Vec`'s doubling from lesson
3: an occasional `O(n)` rehash spread across `n` cheap inserts averages to `O(1)`, which is
exactly why you double the capacity instead of adding a constant. Grow by a fixed +8 and
you'd rehash every 8 inserts forever, and the average would degrade to `O(n)`.

</details>
