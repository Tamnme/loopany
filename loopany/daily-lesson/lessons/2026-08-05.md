### Concept

Rust's **primitive types** are the ones the compiler knows without any library:
integers (`i8`…`i128`, `u8`…`u128`, `isize`/`usize`), floats (`f32`, `f64`), `bool`, and
`char` (a full Unicode scalar — four bytes, not one).

Two compound primitives matter more than the rest, because Track B is about to build on
them.

**Arrays are fixed-length, and the length is part of the type.**

```rust
let a: [i32; 5] = [1, 2, 3, 4, 5];   // type is [i32; 5]
let zeros = [0u8; 100];              // 100 zeros, no loop
```

`[i32; 5]` and `[i32; 6]` are *different types*. The size is known at compile time, so an
array lives on the stack and can't grow. That's the constraint `Vec` exists to lift.

**A slice `&[T]` is a borrowed window into a run of elements** — a pointer plus a length,
nothing more. It doesn't own anything and doesn't copy:

```rust
let a = [1, 2, 3, 4, 5];
let middle = &a[1..4];    // &[i32] — elements 1,2,3 — no copy made
println!("{}", middle.len());   // 3
```

Ranges are half-open: `1..4` is indices 1, 2, 3 — start included, end excluded. That's
why `a[..]`, `a[1..]` and `a[..3]` all read cleanly and why lengths subtract:
`4 - 1 = 3` elements.

Indexing out of bounds is a **panic**, not undefined behaviour — Rust checks at runtime
and stops. That check is the price of the safety, and it's why `get()` exists when you'd
rather have an `Option` than a crash.

### Concept

A **queue** is the other discipline you can impose on a sequence, and it's yesterday's
rule turned around: **first in, first out (FIFO)**. You add at one end and remove from the
other. A stack is a stack of plates; a queue is the line at the counter.

| op | meaning | cost (done right) |
|---|---|---|
| `enqueue(x)` | add `x` at the **back** | `O(1)` |
| `dequeue()` | remove and return the **front** | `O(1)` |
| `peek()` | look at the front | `O(1)` |

```
enqueue 3   enqueue 7   enqueue 1    dequeue → 3   dequeue → 7
front            front       front         front        front
  ↓                ↓           ↓             ↓            ↓
[ 3 ]          [ 3 7 ]     [ 3 7 1 ]     [ 7 1 ]       [ 1 ]
  ↑                ↑             ↑           ↑            ↑
back             back          back        back         back
```

**Here's where it gets interesting — the naive array version is broken.** A stack got away
with an array because it only ever touches *one* end, and it picked the fast one. A queue
touches **both**. Put the front at index 0 and every `dequeue` shifts all remaining
elements down one slot: `O(n)` per removal, exactly the cost you just corrected in
yesterday's Q3. Flip it and `enqueue` pays instead. One end of an array is always slow,
and a queue can't avoid using both ends.

Two real fixes:

**A circular buffer (ring buffer).** Keep the array, but stop moving the elements — move
two indices instead. `head` marks the front, `tail` marks the back, and when either runs
off the end it wraps to 0 (`index = (index + 1) % capacity`). Nothing ever shifts; both
ops are `O(1)`. The array is still contiguous and cache-friendly, and the "empty space"
left behind at the front gets reused as the indices wrap around it.

```
capacity 5, after enqueue 3,7,1 then dequeue twice:

  0   1   2   3   4
[ _ | _ | 1 | _ | _ ]
          ↑   ↑
        head tail        head=2, tail=3 — slots 0 and 1 are free again
```

**A linked list with a tail pointer.** Insert at the head, remove from the tail — or the
reverse. `O(1)` both ways *because* you keep a pointer to each end; without the tail
pointer, reaching the back is an `O(n)` walk. Same pointer-per-element overhead you costed
out in lesson 4.

Where queues show up: task and print queues, message brokers, request buffers, and
**breadth-first search** on a graph — the mirror image of stacks and depth-first search.
Same graph, same code shape; swapping the stack for a queue is the entire difference
between exploring deep-first and level-by-level.

<details>
<summary>Worked answer — open only after you've written yours</summary>

**Q1 — (a) push the opening bracket itself. (b) pop, and the popped bracket must be the
matching opener.** Push `(`, `[`, `{` as you meet them. On a closer, `pop()` and compare:
`)` must pop a `(`, `]` must pop a `[`, `}` must pop a `{`. A stack is the exact shape of
this problem because a closer always matches the **most recent unmatched opener** — that
is LIFO, stated in bracket terms. Walking `([]{})`: push `(`, push `[`, see `]` → pop `[`
✓, push `{`, see `}` → pop `{` ✓, see `)` → pop `(` ✓, end with an empty stack →
**balanced**. Three ways it fails, and each is a one-line check: the pop returns the
*wrong* opener (`(]`), you try to pop an **empty** stack (a closer with no opener, `)(`),
or you reach the end with the stack **non-empty** (unclosed openers, `([`). That last one
is the check people forget.

**Q2 — front to back: `2, 6, 5`; the front is `2`.** Trace it: `4` → `4,9` → dequeue
removes **`4`** → `9,2` → `9,2,6` → dequeue removes **`9`** → `2,6,5`. Compare yesterday:
the identical operation list on a stack left `4, 2, 5` with `4` sitting at the bottom
untouched. Here `4` is the *first thing to leave*. Same data, same operations, opposite
survivors — the discipline is the whole difference.

**Q3 — `dequeue` is `O(n)`; a circular buffer moves the *indices* (`head` and `tail`),
not the elements.** Removing index 0 means sliding all `n-1` survivors down one slot,
every single time. The ring buffer's insight is that the elements never needed to move —
only your idea of where "the front" is. Advance `head = (head + 1) % capacity` and the
vacated slot at the front simply becomes free space that a later `enqueue` wraps around
into. `O(1)`, no allocation, no shifting. The bookkeeping cost is that `head == tail` is
ambiguous between empty and full, so you keep a length counter or leave one slot always
empty — a real implementation detail you'll hit when you write `Queue` in stage B2.

**Q4 — a queue.** "All rooms one step away, then all rooms two steps away" is exactly
breadth-first search, and BFS is a queue: rooms discovered earlier are explored earlier,
so the frontier drains in distance order. A stack gives you the *newest* discovery back
first, so from the first room you'd immediately push deeper into its first neighbour's
neighbour, and you'd be five rooms deep before ever looking at the second door out of the
start — that's depth-first search. Neither is wrong; they answer different questions. BFS
finds the *shortest* path in an unweighted graph precisely because of that level-by-level
order, and DFS doesn't.
</details>
