### Concept

Yesterday's `Vec<T>` owns a heap allocation. That ownership is the whole of today:

```rust
let v = vec![1, 2, 3];
let w = v;                 // v is MOVED into w
println!("{v:?}");         // error: borrow of moved value: `v`
```

Nothing was copied — the three words (ptr, len, capacity) were handed over and `v` is dead.
Rust has to do this: two live `Vec`s pointing at one buffer means two frees of one allocation.

Integers don't move. `i32` is `Copy` — the whole value *is* the data, so duplicating it is
harmless and both names stay usable.

Passing to a function moves too, so `fill_vec(v)` costs you `v`. Two ways out: **return it**,
or **borrow it** (`&v`, `&mut v`) so the function reads without taking. Today's exercises are
four variations on exactly that choice.

### Concept

Every structure so far has been **linear**. A **tree** branches: each node holds a value and
links to children, one **root** at the top, no cycles. A **binary** tree caps it at two
children, `left` and `right`.

A **binary search tree** adds one rule, and everything follows from it:

> **everything in the left subtree < the node < everything in the right subtree**

Read that twice — it says *subtree*, not *child*. A node deep in the left branch still has to
be smaller than the root.

```
        50
       /  \
     30    70
    /  \
  20    40
```

Search 40: compare with 50 → smaller, go left. Compare with 30 → bigger, go right. Found.
**Each comparison throws away an entire subtree** — the same halving as binary search, except
here the structure holds it, so unlike a sorted array you can also insert cheaply.

Cost is the **height** `h`, not `n`. Balanced, `h ≈ log₂ n`: a million nodes, twenty
comparisons. But shape depends on insertion order, and sorted input degenerates into a linked
list wearing tree pointers, `h = n`.

| op | balanced | worst case |
|---|---|---|
| search / insert / delete | `O(log n)` | `O(n)` |

One free payoff: walk left-subtree → node → right-subtree recursively (**in-order traversal**)
and the values come out **sorted**. That's the invariant read out loud.

**Q1.** `50` is the root. `30` < 50 → left. `70` > 50 → right. `20` < 50, < 30 → 30's left.
`40` < 50, > 30 → 30's right. `60` > 50, < 70 → 70's left.

```
        50
       /  \
     30    70
    /  \   /
  20   40 60
```

**Q2 — compare `50`, `70`, `60`: three comparisons.** An unsorted array of 6 needs up to 6 —
no rule about where anything is, so you scan. Each tree comparison discarded a whole branch.

**Q3 — a right-leaning chain, `h = 5`, search is `O(n)`.** Every value is bigger than
everything before it, so each goes right, forever: `10 → 20 → 30 → 40 → 50`, each the right
child of the last. The BST didn't fail — nothing in its rule mentions *balance*. That's why
self-balancing trees (AVL, red-black) exist: they rotate on insert to keep `h ≈ log n`.

**Q4.**

```
      50
     /
   30
     \
      60
```

`30` < 50 ✓ and `60` > 30 ✓ — every parent–child pair is fine. But `60` sits in **50's left
subtree** and `60 > 50`, so the invariant is broken. This is why a validity check must carry a
`(min, max)` range down the recursion rather than just comparing with the parent.

</details>
