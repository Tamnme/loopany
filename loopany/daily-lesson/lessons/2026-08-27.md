## Track A · Rust

### Concept

`Option<T>` has two arms, `Some(v)` and `None`. `None` is *silent* — it says a value is missing
without saying why. `Result<T, E>` is the identical shape with a payload in the empty arm:

```rust
fn generate_nametag_text(name: String) -> Result<String, String> {
    if name.is_empty() {
        Err("Empty names aren't allowed".to_string())
    } else {
        Ok(format!("Hi! My name is {name}"))
    }
}
```

Same `if`, same two branches. Only the return type and the two constructors changed —
`None` → `Err(reason)`, `Some` → `Ok`. Everything you learned about matching carries over:
`if let Ok(v) = …` reads exactly like `if let Some(v) = …`.

Choosing `E = String` means callers can only match on prose — one typo in the message and their
error handling silently stops firing.

## Track B · DSA

### Concept

A search revisits the same position constantly through different move orders. To reuse work it
has to ask "seen this exact position before?" at *every* node — so hashing the whole board each
time is far too slow.

**Zobrist hashing.** Before the game, fill a table of random 64-bit numbers: one per
(piece, square) — 12 × 64 of them — plus one for side-to-move, and a few for castling rights and
the en-passant file. A position's hash is every applicable number XORed together.

The payoff is what happens on a move. You never recompute. A knight going b1→c3 changes exactly
two facts, so:

```
hash ^= Z[white_knight][b1];   // no longer there
hash ^= Z[white_knight][c3];   // there now
hash ^= Z[side_to_move];       // and it's Black's turn
```

Three XORs, O(1), whatever the position. That works because **XOR is its own inverse**:
`x ^ k ^ k == x`. Applying a key twice is the same as never applying it — which is precisely what
"unmake this move" needs, so make and unmake become the same three lines.

Forget the side-to-move key and White-to-move and Black-to-move collapse into one table entry.

<details>
<summary>Worked answer — open only after you've written yours</summary>

**Q2 (a)** `0b0001 ^ 0b1011 = 0b1010`, `^ 0b0110 = 0b1100`, `^ 0b1100 = 0b0000`. The hash is
`0b0000`.

**(b)** `0b0000 ^ 0b1011 ^ 0b0110 ^ 0b1100 = 0b0001` — back where you started. XOR is its own
inverse, so unmake is *literally the same code* as make: no saved copy of the old hash, no stack
of hashes to unwind, nothing to get out of sync.

**(c)** With `+` you'd need `-` to undo, so make and unmake become two different code paths that
have to stay in agreement forever. Worse, addition carries between bits, so nearby positions
produce nearby sums — the hash stops looking random and collisions cluster, which is the one
property the whole table lookup rests on.

</details>
