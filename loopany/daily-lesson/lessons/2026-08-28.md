## Track A · Rust

### Concept

`errors1` gave you a `Result`. Now you have to *pass one along*. The long way:

```rust
let qty = match item_quantity.parse::<i32>() {
    Ok(v) => v,
    Err(e) => return Err(e),
};
```

The short way is one character:

```rust
let qty = item_quantity.parse::<i32>()?;
```

`?` means exactly that `match`. On `Ok(v)` it unwraps to `v` and execution continues; on
`Err(e)` it **returns `Err(e)` from the enclosing function immediately** — the rest of the
body never runs. That's why `?` is a statement-level control-flow operator, not a method.

The catch is the enclosing function. `?` can only give up early if the function it sits in
also returns a `Result` (with an error type the `Err` converts into). It is not a way to
extract a value; it is a way to hand the problem upward.

Put `?` in a function returning a plain `T` and the compiler rejects it outright.

## Track B · DSA

### Concept

Reminder, not a re-teach: a Zobrist hash is a fixed table of random 64-bit numbers — one per
(piece, square), plus side-to-move, castling rights and the en-passant file — XORed together
for whatever the position happens to have. XOR is its own inverse, so a move is three or four
XORs and unmake is the identical three or four.

The whole transposition table rests on one property: **two positions are the same position if
and only if they hash the same.** Both directions have to hold. Today you attack the harder
direction.

Miss one component out of the table and two genuinely different positions collide silently.

<details>
<summary>Worked answer — open only after you've written yours</summary>

Three that all produce the same position with two hashes:

1. **Re-randomising the table.** Generate the keys fresh at startup and a hash saved to disk,
   or shared across two threads with separate tables, means nothing. Not slower — *wrong*, and
   silently: the table returns scores computed for unrelated positions.
2. **Including something that isn't part of the position.** The commonest is the en-passant
   key set whenever a pawn double-steps, even when no enemy pawn can actually capture. Both
   positions are the same to play; one carries an extra XOR. You simply never get a hit — pure
   lost work, no wrong answers.
3. **Drifting from the incremental update.** A make/unmake path that forgets one XOR (castling
   rights after a rook moves, say) leaves the hash correct by *path*, not by position. Reach
   the same square via a different move order and the hashes differ. This is the nasty one: it
   comes and goes with move order.

**Q2** — (3) is detectable: recompute the hash from scratch every N nodes under
`debug_assertions` and assert it matches the incremental one. (1) and (2) look like a healthy
engine with an unhelpfully low hit rate.

</details>
