## Track A · Rust

### Concept

Rust will not let you read a variable that was never given a value. Not a runtime
crash, not a garbage value — the program simply doesn't compile.

```rust
let x: i32;
println!("{x}");   // error[E0381]: used binding `x` isn't initialized
```

The type annotation isn't the problem; the missing value is. Declaring first and
assigning later is legal, as long as every path assigns before the first read:

```rust
let x: i32;
x = 5;             // fine — assigned before use
println!("{x}");
```

The related trick is **shadowing**: `let` a name that already exists and you get a
brand-new variable wearing the old name. That's how you "change" an immutable
binding, and unlike `mut` it can change the type too.

```rust
let spaces = "   ";        // &str
let spaces = spaces.len(); // usize — same name, different variable
```

## Track B · DSA

### Concept

An **array** is a fixed-size block of memory: `n` slots, side by side. That layout
buys you `list[i]` in `O(1)` — the address is just `start + i × size`, one
multiply, no searching. It costs you the ability to grow.

A **dynamic array** (Rust's `Vec`, Python's `list`) fakes growth. It keeps a bigger
block than it needs and tracks two numbers:

```
len      = how many slots are actually used
capacity = how many slots exist
```

`push` while `len < capacity` is `O(1)` — write into the next free slot, bump `len`.
When `len == capacity` there's nowhere to put it, so it **grows**: allocate a new,
larger block, copy every existing element over, free the old one. That push is
`O(n)`.

The interesting part is *how much* larger. Watch what growing by **+1 slot** each
time costs, pushing 8 items:

```
push 1 → grow, copy 0     push 5 → grow, copy 4
push 2 → grow, copy 1     push 6 → grow, copy 5
push 3 → grow, copy 2     push 7 → grow, copy 6
push 4 → grow, copy 3     push 8 → grow, copy 7
                          total copies = 0+1+2+…+7 = 28
```

Every single push copies. 28 copies for 8 items, and for `n` items it's
`n(n-1)/2` — that's `O(n²)` to build the list. Now **double** the capacity instead:

```
capacity 1 → 2 → 4 → 8 → 16 …
push 1 → grow, copy 0
push 2 → grow, copy 1
push 3 → grow, copy 2
push 5 → grow, copy 4
push 9 → grow, copy 8      ← the only grows that happen
```

Grows get rarer exactly as fast as they get more expensive. The copies total
`1 + 2 + 4 + 8 = 15` for 16 items — under `n`, always. Spread over `n` pushes
that's a constant amount of copying each: **amortized `O(1)`**. "Amortized" means
the average over a long run of operations, even though one individual push can
still be `O(n)`.

<details>
<summary>Worked answer — open only after you've written yours</summary>

**Q1 — `len = 5`, `capacity = 8`, 4 elements copied.** The array was full, so it
allocated a block of 8, copied the 4 existing elements into it, then wrote the new
item as the 5th. Capacity doubles from the old capacity, not from the new `len`.

**Q2 — 5 grows, 15 copies.** Capacity goes `1 → 2 → 4 → 8 → 16`, so it grows on
pushes 2, 3, 5, 9 and 17 — but the 17th push never happens, so within 16 pushes
it's 4 grows *plus* the very first allocation. Copies: `0 + 1 + 2 + 4 + 8 = 15`.
Either "4 grows / 15 copies" or "5 including the initial allocation" is fine — the
load-bearing number is that 15 < 16, i.e. fewer copies than items.

**Q3 — `+1` is much worse: `O(n²)` total versus `O(n)`.** Growing by one copies on
*every* push, summing to `n(n-1)/2` copies. Doubling copies on only
`log₂ n` pushes, and those copies sum to under `n` total — so building the list is
linear, and each push is amortized `O(1)`. This is why every real dynamic array
grows by a multiplicative factor.

**Q4 — `O(1)`.** Elements sit in one contiguous block, so the address is computed
arithmetically: `start + 500 × element_size`. The array's length is irrelevant —
one million items or ten, it's the same single multiply-and-add. This is the
property a linked list gives up, which is where Track B goes next.
</details>
