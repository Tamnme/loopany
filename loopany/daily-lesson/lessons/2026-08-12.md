## Track A · Rust

### Concept

A `String` owns its text. A `&str` is a borrowed *view* into text someone else owns. `"e4"`
written in your source is a `&str`.

Neither lets you index by character — `name[0]` does not compile — because one character can
be several bytes. Two ways in:

```rust
let name = "e4";
name.chars().next().unwrap()   // 'e'   — a char
name.as_bytes()[0]             // b'e'  — a u8, which is 101
```

`.chars()` hands you an **iterator**, not a character. That's your first error: you compared
the whole iterator to a `u8`. And because ASCII letters are consecutive, bytes do arithmetic —
`b'e' - b'a'` is 4, which is exactly the file index. No lookup table needed.

## Track B · DSA

### Concept

**Sorting** splits into two families, and the gap between them is the lesson.

**Insertion sort** walks left to right, and pushes each new element back into the sorted part
until it fits:

```
[5, 2, 4, 1]   take 2 → compare with 5, smaller → shift
[2, 5, 4, 1]   take 4 → compare with 5, smaller → shift; with 2, bigger → stop
[2, 4, 5, 1]   take 1 → shifts past 5, 4, 2
[1, 2, 4, 5]
```

Every element can walk past every earlier element, so the work is `n × n` — **`O(n²)`**.

**Merge sort** splits the array in half, sorts each half, then merges the two sorted halves
in one pass. Halving bottoms out after `log₂ n` levels, and each level touches all `n`
elements once — **`O(n log n)`**.

That difference is not a detail. At a million elements it is a million times a million versus
a million times twenty.

The catch: insertion sort is *faster* on tiny or nearly-sorted arrays, because it does almost
no work when nothing needs moving. Real sorts (Rust's included) are hybrids for exactly this
reason.

Chess needs this at phase 6. Alpha-beta search is far faster when the best move is tried
first, so every node sorts its move list — dozens of tiny arrays, millions of times.

<summary>Worked answer — open only after you've written yours</summary>

**Q1.** Start `[3, 1, 4, 2]`.

- Place `1`: it's smaller than `3`, so `3` shifts right → `[1, 3, 4, 2]`
- Place `4`: bigger than `3`, stays put → `[1, 3, 4, 2]`
- Place `2`: shifts past `4` and `3`, stops after `1` → `[1, 2, 3, 4]`

**Q2.** `n²` = **1,000,000,000,000** (10¹²). `n log₂ n` ≈ 1,000,000 × 20 =
**20,000,000** (2 × 10⁷). Merge sort is ~50,000× less work.

For 30 moves, **insertion sort**. `n log n` only wins once `n` is large enough to pay off
merge sort's recursion and its extra buffer; at `n = 30`, `n²` is 900 comparisons of a plain
loop over contiguous memory, and insertion sort quits early when the list is already close to
ordered — which move lists usually are, because the previous iteration ordered them.

</details>
